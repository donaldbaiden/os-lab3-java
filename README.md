Лабораторная работа №3 на Java.

Задача та же, что и в C++ варианте (https://github.com/donaldbaiden/os-lab3): поток main и несколько потоков marker, синхронизация через критические секции и события.

Запуск:
javac *.java
java Main

Сравнение с C++ версией.

По строкам кода получилось почти одинаково: на C++ один файл main.cpp на 145 строк, на Java четыре файла Main.java, Marker.java, MarkerState.java, Shared.java суммарно около 170 строк. Разница в основном из-за того что Java заставляет каждый класс держать в своём файле и обязательно импортировать ReentrantLock и Condition.

Логика синхронизации один в один: pthread_mutex_t заменился на ReentrantLock, pthread_cond_t на Condition, pthread_cond_wait на await, pthread_cond_signal на signal, broadcast на signalAll. Структура цикла marker, ожидание блокировки в main, передача сигнала на завершение конкретному потоку — всё то же самое.

В Java не пришлось писать delete и думать про утечки памяти, массив и объекты MarkerState чистит сборщик мусора. Но появилась обязательная обработка InterruptedException у Thread.sleep, пришлось оборачивать в try-catch.

Цикломатическая сложность одинаковая, ветвлений столько же. Юнит-тесты писать одинаково геморройно и там и там из-за того что вся логика про многопоточность, и тестировать её без специальных инструментов сложно.

Баги при разработке были идентичные — на обеих версиях я сначала забыл сбросить blocked = false и декрементировать blockedCount после resume, и пришлось исправлять в отдельном коммите. То есть это ошибка логики синхронизации, а не языка — она бы случилась на любом языке.

Вывод: если убрать синтаксический сахар и работу с памятью, код практически идентичный. Java чуть многословнее за счёт того что каждый класс в отдельном файле, но проще читается за счёт try-with-resources и понятных имён вроде signalAll вместо broadcast.
